# Schema generation

Payload types are ordinary Python types. This stream sends a dataclass with a fixed-length tuple, a variable-length tuple and an optional field, and declares one example:

```python
--8<-- "docs/examples/payload_schemas.py"
```

## The generated schema

```json
--8<-- "docs/_generated/fragments/payload_schemas/components-schemas.json"
```

The message refers to that schema and carries the example:

```json
--8<-- "docs/_generated/fragments/payload_schemas/channels.json"
```

## How it works

Schemas come from Litestar's own schema generation, the same code that builds OpenAPI schemas, so every model type the application supports works here: dataclasses, msgspec structs, Pydantic models, attrs classes and TypedDicts, provided their Litestar integrations are installed. Each document build uses a fresh schema registry and the application's schema plugins, even when OpenAPI is disabled, and named models end up under `components.schemas`.

AsyncAPI 3 uses JSON Schema Draft07 for inline schemas, so the generated schema is converted to Draft07. A schema construct with no Draft07 equivalent, such as a dynamic reference, raises an error that names its location.

Optional fields keep their `null` alternative and their default. Model aliases, msgspec array-like structs, recursive models and DTO transfer shapes produce the shape that goes over the wire.

## Tuple and schema dialect

A fixed-length tuple such as `tuple[float, float]` becomes a Draft07 positional `items` array with `minItems` and `maxItems` equal to its length; `tuple[()]` has `maxItems: 0`. A variable-length tuple such as `tuple[str, ...]`, or a bare `tuple`, becomes an unbounded array. The document never contains `prefixItems`.

To write a schema by hand, pass a `Schema` from `litestar_asyncapi.spec`, a schema dictionary or a `MultiFormatSchema` as the payload; these are used as given. The official AsyncAPI schema rejects a bare boolean payload, so write `MultiFormatSchema("application/schema+json;version=draft-07", False)` for one.

## Examples

A message's examples come from the first of these that is present:

- examples passed to the decorator or `MessageDefinition`, as in this example;
- examples declared on the model or its schema;
- an example generated by Litestar's example factory, when `AsyncAPIConfig(create_examples=True)`.

Explicit examples pass through the application's type encoders, so they look like real messages. An empty list means no examples, and `null` values are kept. Generated examples are random; prefer explicit ones for documentation that should not change between builds, and for tuples, which the console cannot fill in by itself. Litestar's example factory can need Pydantic: if `create_examples=True` raises `MissingDependencyException`, install `litestar[pydantic]`. When a type has constraints the factory cannot honor, the message gets no generated example and a warning is raised.

## Custom types

A type that Litestar cannot describe needs a schema plugin. Register the plugin and a type encoder on the application, as you would for OpenAPI; this also works with `openapi_config=None`:

```python
--8<-- "docs/examples/native_schema.py"
```

The plugin describes the type in documents only. It adds no decoding or validation at runtime.

## Recap

- Payload schemas come from Litestar's schema generation and are exported as Draft07.
- Fixed-length tuples get positional `items` with exact bounds; explicit examples take precedence over generated ones.
